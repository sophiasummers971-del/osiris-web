## Implemented contracts

| Object             | Binding and validation                                                                                                                                                                                                                                                                                                                                                                                 |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Plan Y             | Strict versioned JSON schema; Task X text and task ID; owner and tenant; each step's description, purpose, justification, dependencies, permitted scope, risks and expected evidence. Duplicate/unknown/cyclic steps are rejected. Recursive freeze plus canonical SHA-256 includes every field and version. Key order/whitespace do not change logical identity.                                      |
| Authority approval | Canonical, domain-separated Ed25519 receipt verified against a host-pinned authority key. Binds exact plan hash/version, task ID, owner, tenant, approval ID, issuance and expiry. Changed plan content/version invalidates the old receipt.                                                                                                                                                           |
| Agent handover     | Independently pinned contract-issuer signature; individual contract ID; `NR-00001`-style five-digit agent identity and registered key fingerprint; approval, plan, task, owner, tenant, step, job, target, commit, tools, zones, expiry, integer budgets and ruleset hash. Permissions and budgets cannot exceed the approved step.                                                                    |
| Agent request      | Agent signs a separate admission/action domain, exact contract hash, plan/version, step, owner/tenant/task, nonce and short lifetime. Naming an agent is insufficient without its registered private-key proof. Registry keys are copied/pinned and distinct identities cannot share one key.                                                                                                          |
| Admission          | Approval, contract and agent request must verify before entering PR #48's facade and the existing Rule Zero launcher. Atomic contract/agent/step claims prevent concurrent reuse across gate instances sharing storage. One agent and contract per independent step per plan; no fallback when persistence fails. Job/request snapshots and freshness are rechecked after awaits.                      |
| Synthetic actions  | Authenticated tool/zone/ruleset violations synchronously set REVOKED and return DENY/REVOKE. Subsequent actions cannot call the synthetic executor. Budgets reserve before awaits; action nonces are single-use. Pending actions recheck revocation before callback. A forged violation cannot revoke another agent's grant. Uncertain authenticated callback/store failures revoke rather than retry. |

The API is additive: `createPlanY`, `verifyPlanApproval`, `verifyAgentContract` in `scripts/rule-zero/plan-y.mjs`; `createPlanYAdmission` in `scripts/rule-zero/plan-y-admission.mjs`. There are no source changes to PR #47/#48's existing modules, routes, configuration or workflow. The gate does not sign receipts and requires only public verification keys. Synthetic signing helpers and private keys remain in the test file.

## AMBER limitations and independent-review gates

- **No production identity or capability boundary.** Fixture signatures prove cryptographic possession of pinned keys, not that a real person/tenant authorized them. Key enrollment, custody, revocation and owner verification remain operational gates. Host constructors, callbacks and pins must be protected; direct access outside this gate is not mediated. Signed ruleset hashes and zone labels do not themselves enforce filesystem, network or tool isolation.
- **Dependent steps fail closed.** Plans validate dependency DAGs, but no independently verified completion-evidence protocol exists yet; admission returns `DEPENDENCY_EVIDENCE_UNSUPPORTED`. Expected evidence is hashed plan metadata, not a completed-work attestation. No scheduler or automatic agent replacement is implemented.
- **No automatic plan supersession.** Changed content requires a new signature/hash. A separately retained, unchanged older plan can remain valid until expiry; there is no authoritative latest-version or early owner-revocation registry.
- **Local state and bounded claims, not distributed security.** Tests use the inherited single-filesystem staging nonce store. Claim retention, failover, disaster recovery, distributed counters and tamper-resistant audit require separate review. Local state does not restore active contracts after restart. Reservations burn on failure; reassignment requires new authorized plan/contract identities. Maps grow for the gate lifetime and need host-level admission bounds.
- **Synthetic budgets only.** Calls are locally counted; token and cost charges are signed declarations. A real tool adapter must independently measure actual usage and apply resource limits. This prototype does not certify actual spend or external work.
- **Revocation blocks future local callbacks, not completed effects.** Already-running callbacks cannot be terminated by this library. Missing completion audit/receipt or an uncertain executor result may follow an action that already happened; RED cannot undo it. No cancellation or process-termination claim is made. Authentic signed request replay can deny/revoke a grant, so denial-of-service resistance remains limited.

Independent review must rerun both verification commands at the exact source SHA, inspect the signature domains and canonical schemas, audit all real host adapters and storage lifetimes, and establish mandatory capability mediation before proposing production use. To roll back this draft, use a normal revert on its own branch; do not reset either prior PR branch. Nothing was deployed and no live credentials, databases, agents or permissions need rollback.
