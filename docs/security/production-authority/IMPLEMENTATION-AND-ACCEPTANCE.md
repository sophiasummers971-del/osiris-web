# Phased implementation and staging acceptance

**Future work specification only.** This design PR does not authorize provisioning, migrations, production connections, credential changes, deployment or live agents. Each later phase needs its own scoped development proposal and authorization. Current prototype restrictions remain unchanged.

Email, inference, bearer download URLs, arbitrary HTTP and other non-fenceable effects do not automatically advance with the first DB adapter.

## Interface/data contract to implement later

No DDL or connections are included here. Future schema/API reviews must preserve:

- `tenant_authority`: stable tenant/object/authority ID, epoch, fence counter, resource/store incarnation, mode `FROZEN|ACTIVE|RECOVERING`, event sequence/head and external checkpoint head.
- `enrolled_subject`: trusted owner/reconciler/workload identity, key ID/algorithm, tenant, role, status and explicit revocation. Role or tenant strings from client metadata are not enrollment.
- `plan_approval` / `handover`: exact canonical plan/version/task/owner/tenant and receipt hashes; immutable scoped contract; dependency/evidence requirements; lifetime and budget reservation. No automatic old-version supersession without policy.
- `consumed_identity`: permanent tenant tuple for job, contract, agent, exact-plan step and receipt bindings. A recovered target imports the complete consumed manifest before becoming ACTIVE.
- `operation`: unique tenant operation ID, claim, argument/resource/adapter digest, epoch/fence/incarnation, actual budget reservation and `PREPARED|CHECKPOINTED|IN_FLIGHT|ACKNOWLEDGED|UNKNOWN|QUARANTINED` state. State transitions append events; unknown does not become reusable on a timer.
- `effect_receipt` / `reconciliation`: provider/DB commit identity and resource version, independent process/network observations, signed reconciliation manifest, current authority/checkpoint heads and explicit disputed/unknown outcomes. Agent text or a log line is not independent receipt evidence.

The five-digit `NR-xxxxx` label space is finite. Permanent consumption requires a reviewed, explicitly versioned namespace expansion before exhaustion; never wrap counters or silently reuse an old identity.

Methods: enroll/revoke identity, register supervisor, reserve claim/budget, prepare/dispatch fixed operation, query its durable outcome, freeze, reconcile and approve recovery. No generic `execute(callback)`, arbitrary target, raw SQL, caller-controlled registry/key, force-reset or silent compatibility switch is a production API. Audit queries must not mutate authority or mint grants.

## Isolated test setup

Use two or more independent supervisor processes/hosts with distinct workload keys, separate ephemeral local state and one canonical tenant authority. Include a second tenant and multiple ordinary users. Use only synthetic records/files/addresses, fixed mock providers and disposable resource functions. Deliberately restore/fork staging stores; never point restore tools at production.

Evidence must include exact source/build digest, runtime/region/plan/configuration, public key fingerprints (no secrets), test seed, synchronized event history, independent resource-side operation/effect count, grant/epoch/checkpoint sequence, injected fault location, real process identity/exit observations and command/run logs. Archive signed manifests in the independent evidence domain. A client GREEN/RED count alone is insufficient.

The following numbers are **proposed acceptance targets**, not observed results or vendor SLAs. A failed performance target may justify reducing supported load/scope; it never justifies fail-open behavior, deleting consumed claims or weakening approval/isolation.

Use real hosted staging for vendor PITR, effective roles/bindings, cache, identity and partition behavior; local emulation cannot establish those guarantees. Existing 324 Rule Zero tests and 194 repository tests must continue to pass, but are only the regression layer. New hosted evidence must name its exact build/configuration and an observer independent of the implementation author.

## Retention and release gates

Proposed policy for review: redact content/secrets before logging; retain full security event metadata for 90 days and approval/recovery/receipt manifests for 365 days. Retain minimum consumed-identity tombstones for the authority's active/replay lifetime; do not delete them merely because a token expires. Opaque IDs/hashes can still be personal or linkable data. Privacy/custody review must approve actual periods, encryption, deletion/tenant-retirement and legal-hold procedures before any real data is used.

Audit capture must distinguish accepted intent, actual effect, provider acceptance, observed termination and reconciliation. Signed daily manifests/checkpoints and an independent verifier expose truncation; raw logs and hash chains in the same restored DB are not independent custody. Post-effect audit loss marks UNKNOWN and inhibits retry. No account token, private key, authorization header, raw prompt/attachment or unnecessary personal data belongs in evidence.

Rollback of future code means freeze capability release and preserve consumed state, then revert a reviewed artifact. Reverting into unfenced mode, restoring a DB snapshot as an availability shortcut, or clearing crash locks is prohibited. Permission to open this design PR is not permission to perform any phase above.
