# One synthetic effect and its proposed database boundary

**Specification, not a migration or implemented function.** Target PostgreSQL 17 semantics for the first review; exact hosted version/extensions/grants must be checked before implementation. No SQL in this document has been applied.

## Tenant, payload and authorization

[synthetic-fixture.json](synthetic-fixture.json) defines the sole enrolled synthetic tenant, owner, resource, Task X, step, job, operation and distinct NR-xxxxx agent. IDs were generated locally; no real subject or record was copied. A second random tenant used in a negative case is an **unenrolled input**, not a second supported tenant. Each independent test run generates fresh job/operation/approval/contract/agent keys; consumed identities are never reused to make a healthy test pass.

The only operation is `appendSynthetic`, target `p2/db/synthetic_records`, zone `p2/synthetic/db`, kind `synthetic.marker.v1`. It inserts one marker into the fixed resource, increments resource version from 0 to 1, consumes its one-use permit/claims/budget and appends one audit event in the **same database transaction**. It accepts no SQL, table name, URL, runner, tool registry, credential broker or authorization callback. One call, one row and 1,024 UTF-8 payload bytes maximum. Cost reservation is a synthetic 100,000-micro-unit ceiling, not a claim to meter real provider billing.

The proposed P2 plan profile requires exactly one machine-checked `approved-arguments-sha256:<64-hex>` entry in the signed step's `expectedEvidence`; it must equal the canonical full argument digest, including marker, resource and expected version. Missing/duplicate/conflicting entries deny. This profile adds no field to the inherited Plan Y schema, but its enforcement is **future gateway work**, not a guarantee of the existing helper.

The trusted registrar independently verifies canonical Plan Y, exact owner approval signature, individual contract/agent proof, issuer enrollment/tenant, scope/expiry, Rule Zero admission, current authority fence and retained pre-effect intent. Plan hash/version, task/step, owner/tenant, approval/contract/agent/job IDs, resource/version, operation/argument digest, ruleset, budget, artifact/key pins and database incarnation must agree. Missing/changed/extra fields, wrong signatures/keys and expanded permissions deny. No `verified: true` supplied by an agent is accepted.

The registrar's credential is a **trusted authorization capability**. Database functions do not pretend that a hash or JSON boolean independently verifies Ed25519. Signature verification is performed by fixed reviewed gateway code with pinned public keys; the DB trusts this isolated principal to register only that result. A future requirement to verify signatures inside Postgres needs a separately reviewed supported verifier and revised contract; pgcrypto is not assumed to provide Ed25519 verification.

## Logical records and constraints

All relations are in private `rz_p2_private`; none is an exposed REST schema. Schema/type/function definitions are pinned in the eventual reviewed artifact.

| Record                | Immutable or guarded contents / invariant                                                                                                                                                                                                                           |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `resource_gate`       | Exactly one seeded tenant/resource row; incarnation, epoch, supervisor ID/fence, transition ID, mode FROZEN/ACTIVE, trusted-time high-water, artifact pins and checkpoint-head digest. No runtime role can insert a replacement row or reset counters.              |
| `permits`             | Unique (tenant, operation ID), immutable full verified authorization bindings and argument bytes/digest; pinned workload principal; trusted intent/checkpoint receipt hash; deadline. Only status can move REGISTERED → CONSUMED or QUARANTINED.                    |
| `consumed_identities` | Unique (tenant, identity kind, ID) for this one-use job, contract, agent/step assignment and approval use. Claim insertion is atomic with append; external authority burns the same tuples **before dispatch**. No runtime delete, TTL release or upsert overwrite. |
| `resource_state`      | Fixed resource ID, version, reserved/used row+byte budget. Guarded increments only; no caller-selected resource.                                                                                                                                                    |
| `synthetic_records`   | Unique (tenant, operation ID) and unique one-use job; stored marker/kind, authorization digest and resulting version. INSERT-only for effect function owner.                                                                                                        |
| `audit_events`        | Unique per-tenant sequence, operation ID, before/after version, effect digest, authorization/fence/incarnation and previous-event hash. INSERT-only; same transaction as effect. Local chain is not independent retention.                                          |

An immutable body cannot be edited by registering the same ID again. Duplicate registration is a conflict; reconciliation reads an existing record through a separate observer interface. The append function never silently returns a cached success or treats `ON CONFLICT DO NOTHING` as a new execution.

## Proposed roles and positive allowlist

Every workload login is NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOREPLICATION, NOBYPASSRLS, NOINHERIT, owns no object and has **no role membership/SET ROLE path**. NOINHERIT alone is insufficient. All credentials are generated only after separate authorization, scoped to the new staging database and held outside workers.

| Role                                                           | Exact positive privilege proposal                                                                                                                                                                 | Excluded capabilities                                                                                                               |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `rz_p2_schema_owner`                                           | NOLOGIN; owns private/API/control schemas and tables; trusted migration owner only.                                                                                                               | No runtime login, workload membership or secret in host/worker. Owners remain powerful TCB, even without BYPASSRLS.                 |
| `rz_p2_effect_owner`                                           | NOLOGIN; owns append function; SELECT/UPDATE gate lock columns, SELECT/UPDATE permit status and resource state; INSERT claims/marker/audit plus narrowly required SELECT for validation/receipts. | No table ownership, CREATE, DELETE/TRUNCATE, arbitrary network/cron/admin function EXECUTE or control-function EXECUTE.             |
| `rz_p2_control_owner`                                          | NOLOGIN; owns fixed registrar/fence functions, only required private-record SELECT/INSERT and guarded gate/status UPDATE.                                                                         | No marker INSERT or append-function EXECUTE; cannot grant privileges or mint arbitrary effect rows.                                 |
| `rz_p2_actuator`                                               | LOGIN, max 2 connections; CONNECT, USAGE of `rz_p2_api`, EXECUTE of append function only.                                                                                                         | No private/control schema USAGE, direct table DML/SELECT, public RPC, extension networking, role switching or provider secrets.     |
| `rz_p2_registrar`                                              | LOGIN, max 1; CONNECT, USAGE `rz_p2_control`, EXECUTE register function only.                                                                                                                     | No append, fence transition, marker write or administrative access.                                                                 |
| `rz_p2_fence_controller`                                       | LOGIN, max 1; CONNECT, control-schema USAGE, EXECUTE freeze/install/activate only, as fixed protocol operations.                                                                                  | No permit registration, marker append or general SQL mutation. Trusted control plane can deny/transition, not invent approved work. |
| `rz_p2_observer`                                               | LOGIN, max 1; CONNECT, USAGE `rz_p2_observe`, SELECT on read-only synthetic evidence views only. Independent custodian holds credential.                                                          | No execution, grant, freeze, mutation or secret read. Views expose only synthetic evidence and no security-definer escape.          |
| anon/authenticated/service_role/PUBLIC and agent OS identities | **No** staging API/control/private/evidence schema privileges or function EXECUTE. Agents have no DB login at all.                                                                                | Existing production managed roles are not used as workload principals.                                                              |

Proposed role statement for the actuator, **review text only**:

```sql
CREATE ROLE rz_p2_actuator NOLOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE
  NOREPLICATION NOBYPASSRLS NOINHERIT CONNECTION LIMIT 2;
-- Remains NOLOGIN until separately authorized credential enrollment.
-- Later positive grants, only after the fixed function exists:
GRANT USAGE ON SCHEMA rz_p2_api TO rz_p2_actuator;
GRANT EXECUTE ON FUNCTION rz_p2_api.append_synthetic(uuid, text)
  TO rz_p2_actuator;
```

The function is SECURITY DEFINER, VOLATILE, PARALLEL UNSAFE, fixed `search_path = pg_catalog, pg_temp`, with fully schema-qualified tables/types/functions/operators and no dynamic SQL. Creation and revocation of default PUBLIC EXECUTE must be in one transaction. Apply default-privilege revocations for **each actual creating owner**, not only the deployer. Private/control schemas must never be writable by callers; no caller-controlled GUC/JWT claim authorizes an effect.

This positive table is not a complete executable hardening script: inherited/PUBLIC grants, database TEMP/CREATE, schema USAGE, built-in privileged roles, all function overloads and managed extensions must be enumerated and denied as necessary in the **new disposable project**. Revoking a grant from a workload does not cancel a PUBLIC grant. No `http`, `net`, `dblink`, cron, filesystem, foreign-server, signaling or unsafe definer capability may remain reachable. If managed defaults cannot meet this, staging activation is blocked; this proposal does not authorize weakening the allowlist.

## Fixed interfaces and transaction

| Interface                                                                                                                   | Caller / semantics                                                                                                                                                                                                                                              |
| --------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `rz_p2_api.append_synthetic(operation_id uuid, argument_digest text)`                                                       | Actuator only. Returns a tentative typed receipt; no tenant/payload/scope/key/target argument. Exact immutable bytes come from the registered permit. The digest argument is exactly 64 lowercase hexadecimal characters; it is not a signature or signing key. |
| `rz_p2_control.register_verified_permit(registration jsonb)`                                                                | Registrar only. Strict versioned exact-field schema, bounded size, same row-lock order, valid current gate and immutable body. Stored principal derives from pinned server configuration, not a supplied role.                                                  |
| `rz_p2_control.freeze(incarnation uuid, epoch bigint, transition_id uuid)`                                                  | Controller only. Compare-and-swap exact current state; lock gate and set FROZEN; receipt contains old/new mode and last committed resource version.                                                                                                             |
| `rz_p2_control.install_fence(transition_id uuid, old_fence bigint, new_epoch bigint, new_fence bigint, evidence_hash text)` | Controller only, gate remains FROZEN; exact expected incarnation; strictly increasing epoch/fence, independent recovery evidence required by controller. No reset or auto-increment-on-error. Incarnation change requires new quarantined endpoint procedure.   |
| `rz_p2_control.activate(transition_id uuid, checkpoint_receipt_hash text)`                                                  | Controller only; exact installed transition and independently verified checkpoint binding; never activates an old transition or edits permits. DB relies on controller verification, not the hash alone.                                                        |
| `rz_p2_observe.*` read-only views                                                                                           | Observer obtains effect/claim/audit/gate/permit projection in one primary consistent read transaction. No executing the append function to discover whether it ran.                                                                                             |

Append must use this ordered algorithm under one short DB transaction (proposed statement timeout 2 seconds, lock timeout 250 ms; enforced by trusted adapter and independently reviewed database settings). No hidden reconnect, driver replay, prepared transaction or retry:

1. Verify `session_user` is the pinned actuator login; do not use `current_user` as proof inside a definer function. Lock the fixed gate FOR UPDATE first; absence, unexpected tenant/resource/incarnation, non-ACTIVE mode or counter overflow denies. All control functions lock this same row first.
2. Lock the existing operation permit. Compare digest and every stored pin to gate state: epoch, supervisor fence/identity, adapter/build, resource, tenant, approved owner/plan/version/task/step, job/contract/agent, ruleset, budget and retained intent reference. Require REGISTERED, exact caller binding and no revocation/quarantine.
3. Check trusted time at this guard point: permit/approval/contract bounds, DB clock within approved skew (proposed 250 ms) of recent independently sampled authority time and no backward jump below high-water. Large jump/skew freezes dispatch; never repair by extending expiry. Epoch ordering uses integers, not time. Reliable hosted clock bounds remain an approval gate.
4. Lock claims/budget/resource in documented order. Reject consumed identities, insufficient budget, payload >1,024 bytes, wrong fixed marker kind or unexpected resource version. Never update authorization fields to match.
5. Insert permanent consumed identities, reserve/use exactly one row, append marker, advance resource version and append audit event together. Any check/error/audit insertion failure rolls back **all** of this transaction. The external authority's burned intent still remains consumed.
6. Return a tentative receipt (operation, authorization/argument/effect digests, resource version, audit sequence, incarnation, epoch/fence). Actuator commits. A function return, log message, connection close or receipt before COMMIT is not completion. Independent observation and checkpoint publication are required by [the recovery protocol](FENCING-AND-RECOVERY.md).

The authorization linearization point is the successful guarded resource transaction's ordering under the gate lock. A transaction authorized before a freeze/expiry guard can finish later; no claim of instantaneous external cancellation is made. SQL row locks and definer safety semantics are from [PostgreSQL locking](https://www.postgresql.org/docs/17/explicit-locking.html), [CREATE FUNCTION](https://www.postgresql.org/docs/17/sql-createfunction.html) and [CREATE ROLE](https://www.postgresql.org/docs/17/sql-createrole.html); this specific protocol is a proposed engineering design, not a vendor guarantee.
